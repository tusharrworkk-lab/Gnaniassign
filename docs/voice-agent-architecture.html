1. System purpose and operating principles

The system is a personal phone assistant that can receive a caller’s speech, understand the request, use user-specific context, produce a concise spoken response, retain approved memory, and later learn from reviewed interaction data. It is designed to begin as a single-user system and evolve into a configurable multi-tenant platform.

PrincipleArchitectural consequence
Voice must feel responsiveSTT, LLM, and TTS are streaming/remote services; the server orchestrates rather than hosts a large LLM.
Never let an unvalidated classifier degrade conversationsThe generic LLM remains customer-facing. MiniLM labels stored data asynchronously and humans approve final labels.
Memory must be useful but boundedWorking memory is per-session; episodic memory is customer-scoped and limited to recent history; order context is a small sliding window.
Prompts are product configurationPrompts are stored as tenant-scoped, versioned trees with cache layers and one active version.
Telephony is an adapter, not business logicVoiceLink/SIP/WebSocket transport must feed a provider-neutral voice layer; the agent graph remains unchanged.
Customer data is sensitiveTranscripts, phone numbers, memory, credentials, and KYC information require retention, access control, encryption, and consent policy.

4. End-to-end lifecycle

4.1 Inbound call lifecycle

  1. Call arrives. A purchased DID is routed by VoiceLink to the registered WebSocket bot.
  2. Identity resolution. The telephony adapter validates provider authentication, creates a provider call record, resolves the caller against the product account/customer mapping, and creates an internal session UUID.
  3. Audio ingress. VoiceLink’s documented media is base64-encoded 8 kHz mono A-law. The adapter must decode A-law, resample to the STT contract if necessary, frame audio correctly, and stream it to Gnani STT.
  4. Final STT segment. Only VAD-closed/final transcript text becomes an agent turn. Exact STT segments are retained for the optional end-of-call judge.
  5. Context assembly. The agent loads bounded episodic history, preloaded account/order context, current working memory, active prompt-tree instructions, and approved knowledge.
  6. LLM generation. The generic agent invokes the configured hosted LLM. The current personal prompt requires a transparent AI disclosure, privacy boundaries, and explicit authorization for outbound calling.
  7. Output streaming. LLM chunks flow to Gnani TTS; audio is converted/framed for VoiceLink and returned on the same WSS connection. Barge-in policy determines whether incoming STT is suppressed while speech plays.
  8. Persistence. The turn is written to episodic memory and the analytics ledger. The response does not wait for offline analysis.
  9. Call end. The full structured transcript is persisted. If enabled, Bedrock judges only STT text for intent and separately judges STT+LLM pairs for conversational quality.

4.2 Current text/API lifecycle

POST /v1/turn { customer_id, session_id?, text }
  → API-key validation
  → session registry get/create
  → TurnSession.ask(text)
  → response { session_id, answer, intent }

POST /v1/webhooks/call { call.started | transcript.final | call.ended }
  → HMAC validation
  → transient registry keyed by supplied call_id
  → TurnSession work / call finalization
Current limitation: the API registry key supplied by a caller/provider is not persisted as the internal TurnSession.session_id. This is acceptable for local testing only. VoiceLink requires a durable call-to-session bridge table before production use.

4.3 Outbound call lifecycle

  1. The owner explicitly authorizes the target, purpose, timing, and information allowed to be shared.
  2. The product creates an auditable outbound request. The LLM never claims that a call was placed without a tool-confirmed result.
  3. The VoiceLink Add Lead request uses the configured DID; for India the documented target is a 10-digit customer_number with country_code="91" separately.
  4. VoiceLink routes outbound audio to the WebSocket bot; the same media adapter owns the session and logs the provider call ID.

5. Memory, knowledge, and prompt architecture

5.1 Four kinds of context

Working memoryOne session/callStructured facts inferred during the current dialogue: requested action, order ID, preferences, unresolved question.Prevents repeated questions during a call.

Knowledge baseDurable, approvedIntent-scoped chunks with title, content, status, priority.Provides product/policy facts; it is not conversation memory.

5.2 Prompt tree and cache path

request for (tenant_id, agent_id)
  → L1 process cache (fastest)
  → optional Redis L2 cache (shared across instances)
  → PostgreSQL authoritative prompt tree
     prompt_trees → prompt_versions (one active) → prompt_nodes
  → rendered instruction plan supplied to generic agent

Prompt nodes support parent/child relationships, JSON conditions, priority, enabled flag, draft/active/archive versions. The database enforces at most one active version per tree. A cache miss may query PostgreSQL; ordinary warm turns should not.

6. Intent classification and continuous learning

6.1 Current classifier position

The retail MiniLM is a fine-tuned dual-encoder classifier with nine labels: track_order, return_item, cancel_order, refund_status, wrong_item, size_issue, payment_issue, delivery_address, and other. It scores transcript text against fixed label descriptions.

Current safety decision: the generic agent is the live agent. MiniLM is disabled from deciding live routing because earlier live results degraded response quality. It is appropriate to run MiniLM later as shadow/offline inference.

6.2 Nightly learning loop

conversation_turns where classifier_intent IS NULL
     ↓ (nightly cron; model loaded once on CPU)
nightly_intent_review.py
     ↓
candidate classifier_intent + confidence written to PostgreSQL
     ↓
private Telegram digest: turn ID, text, predicted label, confidence
     ↓
human review sets final_intent
     ↓
export only final_intent rows to reviewed JSONL
     ↓
offline Colab training + held-out evaluation
     ↓
new model version is tested in shadow mode before any live use

Telegram is a review notification channel, not the source of truth. It is deliberately capped to prevent message floods; PostgreSQL retains the complete review queue. Raw transcript sharing requires a private channel, bot access controls, caller consent, and a retention policy.

6.3 Bedrock conversation judge

  • Intent judge: receives final STT text only. It does not receive the LLM answer, avoiding intent contamination by the agent response.
  • Flow judge: separately receives STT/LLM pairs and detects observable corrections, negation, repeated fact requests, and lack of adaptation.
  • Rule governance: generated do/don’t guidance is stored as a candidate. A person must activate it before it influences prompts.

  • Add tenant_id to all customer-facing tables before a multi-tenant/D2C launch; prompt trees already have it, conversations do not.
  • Add a partial index for the nightly queue: WHERE classifier_intent IS NULL.
  • Add classifier_model, classified_at, and classification_batch_id for auditability across model versions.
  • Define a transcript retention/deletion job. The same sensitive content may exist in episodic memory, turn ledger, and call transcript.

8. VoiceLink integration architecture

8.1 Control plane: documented API flow

  1. Reseller onboarding, email verification, KYC, and wallet/plan setup.
  2. Discover DID types with GET /reseller/did-types; do not hard-code catalog IDs or series names.
  3. For a direct-purchase DID: list inventory → lock DID → retrieve server summary → explicitly confirm purchase.
  4. Create a WebSocket Bot with a public wss:// URL and optional HTTPS callback URL.
  5. Create an inbound DID routing record with WebSocket Bot mode.
  6. For outbound calls, verify active DID, routing, wallet/channels, then use Add Lead with documented India number formatting.

8.2 Media plane: adapter contract

VoiceLink WSS event
  → verify connection/provider authentication
  → map provider_call_id to telephony_calls + internal TurnSession
  → decode base64 A-law 8 kHz mono audio
  → resample/frame for Gnani STT
  → final transcript → TurnSession
  → Gnani TTS PCM output
  → resample/encode base64 A-law 8 kHz mono
  → return VoiceLink media frames
Vendor input required before implementation: exact JSON bodies for connected/start/media/mark/clear/transfer/stop, WSS authentication mechanism, outbound media field names, message sequencing, audio frame duration, retry semantics, and static-IP allowlisting behavior. Event names alone are insufficient to build a correct telephony adapter.

8.3 Personal mobile call forwarding

A VoiceLink DID is not automatically connected to the owner’s ordinary mobile number. The owner’s mobile carrier must support conditional call forwarding (no answer, busy, or declined/rejected) to the purchased DID. Test direct DID calling first, then configure carrier-side forwarding. Carrier feature codes, charges, and rejected-call behavior must be confirmed with the SIM carrier.

11. Performance, capacity, and resilience

11.1 Latency budget

StagePrimary latency sourceDesign control
Audio to final STTNetwork + VAD silence thresholdPersistent provider connection, correct frames/sample rate, tuned VAD.
Intent routingDisabled from live path currentlyGeneric agent first; MiniLM runs nightly/offline.
LLM first tokenBedrock/provider network and inferenceShort prompt, prompt cache, concise output budget, stream chunks.
TTS first audioProvider responseStream immediately; optional latency cue policy must not block actual speech.
DatabaseNetwork/disk queryLoad account window at call start, cache prompt plan, asynchronous analytics where possible.

11.2 Initial capacity position

With remote STT/TTS/LLM and no local Laya/model runtime, a 2 vCPU/8 GB VM is suitable for a pilot. Start with a hard cap near five simultaneous active calls. The true bottlenecks are VoiceLink/Gnani/Bedrock quotas and network latency, not the 120B model memory, because it is never loaded locally. If live audio is proxied continuously, keep the cap conservative until load-tested.

11.3 Failure behavior

FailureExpected behavior
STT unavailableDo not fabricate transcript. Tell the caller a technical issue occurred or transfer/end according to an approved fallback.
LLM timeoutUse one concise retry/fallback statement; do not repeat a canned “I will check” loop.
TTS unavailablePreserve text/logs; end or transfer call safely. Do not consider text generation a completed voice reply.
PostgreSQL unavailableDecide explicitly: fail closed for personalised data, or run stateless with no memory persistence. Never imply data was saved when it was not.
Redis unavailableFall back to process cache/PostgreSQL prompt lookup; Redis must remain optional.
Worker restartCurrent in-memory registry loses ownership. The future telephony/session mapping must be durable and Redis-backed before multi-worker deployment.

12. Operations, observability, and runbooks

12.1 Metrics to record

  • Call count, concurrent calls, call duration, answer/hangup/transfer outcomes.
  • STT final latency, LLM TTFT, LLM completion, TTS first-audio time, playback completion, total turn latency.
  • Provider failures/retries by STT, LLM, TTS, VoiceLink.
  • Prompt cache hit rate, database query latency, active sessions, queue/backlog of unclassified turns.
  • MiniLM label distribution/confidence drift, review acceptance/correction rate, and model version.

12.2 Logs and traces

  • Use a correlation ID based on the internal session UUID; preserve provider call ID in the telephony bridge table.
  • Never log bearer tokens, raw credentials, OTPs, or unredacted sensitive values.
  • ACIL tracing is optional and must never block a live response.
  • Full transcript logs require access control and a documented retention policy.

12.3 Daily operator routine

  1. Check service health and error-rate dashboard.
  2. Review failed/abandoned call records and external-provider errors.
  3. Read the private Telegram MiniLM digest, then approve/correct labels in the review tool.
  4. Inspect flagged conversation flow and activate only reviewed do/don’t rules.
  5. Check disk/database growth and backup success.

0009      memory = dict(current)

0011      memory["active_topic"] = topic

0017          if match:
0018              memory[name] = match.group(0)[:80]
