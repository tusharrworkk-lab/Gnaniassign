# Brain notes — 7 October 2026

Notes from the working session on a phone assistant and the voice pipeline behind it. The product shape (a personal assistant that answers and places calls, talks from a card, books meetings, and writes notes) was set earlier. Today was about how audio moves, and how Laya routes a turn to subagents without waiting for the end of the utterance.

## Call audio

WebRTC is only the live audio pipe between a caller and the app. It carries the caller’s voice in and the assistant’s voice out. It does not run the language model, write notes, or tap other apps.

For “use my voice and operate this phone,” the native path is enough: `AudioRecord` for the microphone, `AudioTrack` for the reply, and an accessibility service for the taps. WebRTC is not part of that version.

A second person on the line is different. Android’s phone-call APIs show the incoming-call screen and route the earpiece. They do not hand the app the two voice streams of a normal SIM call. The assistant hears and speaks on calls the app owns: the cell is forwarded to a number the app registers, or the call is placed through the app.

The assistant can still read the normal call log, so it knows who rang. Audio of a plain SIM call stays in the phone stack.

Outbound calls use the same voice path. The app looks up the contact, says what it is about to do, waits for a yes, places the call, and identifies itself as the assistant at the start.

### Two connections, not one

Registration stays up all day so a call can arrive. A foreground call service holds that signaling connection and is exempt from battery optimization. No audio flows until a call connects.

The audio session stays open for the whole call, both directions at once. Do not open a new connection per sentence.

- Caller audio arrives as short frames, about 20 ms each, and is forwarded to a speech-to-text socket that also stays open for the whole call.
- The return path is the same session. Send silence while they talk. Write synthesized speech into that same stream when a reply is ready.
- If they speak over the reply, stop the synthesized audio, return to silence, and keep their frames going to speech-to-text.

When the call ends, close the audio and the speech socket. Leave the registration up. The microphone is open only during a call.

## Laya as the decision step

Laya (`convaiinnovations/laya`, package `laya==0.4.0`) replaces a Jev-style decision call. It is a non-autoregressive model: one forward pass, typed answers, probabilities. It does not write text and it does not invent a list of intents.

The state passed to Laya is the last few turns plus the current text. The general system prompt stays with the subagent that will speak. Questions are a closed set defined in code. `result["answers"]` is already the route. Gate on `confidence`. Ignore `action.act_probability`; it stays near 1.0 and is not a useful signal.

Sketch of the route questions:

- `book_meeting` — book, move, or cancel
- `take_note` — save this turn
- `about_me` — who the user is or what they do
- `needs_reply` — answer, clarify, or hand off

Laya does not extract open parameters (name, email, time). It picks the route. The subagent for that intent extracts the slots and writes the sentence the caller hears.

Load the multilingual checkpoint for a voice turn. It covers Hindi and English. Preload it once and leave it resident. Do not preload every checkpoint.

### Measured on this machine

GPU: NVIDIA GeForce GTX 1650 Ti, 3.6 GB usable.

| Run | What happened | Time for 4 questions |
|---|---|---|
| Preload every checkpoint | Out of memory, fell back to CPU | 323 ms |
| One multilingual checkpoint, FP32 on GPU | Weights on CUDA, about 1.2 GB | 323 ms |
| Same checkpoint, FP16 on GPU | About 627 MB | 241 ms |

The model card’s ~33 ms figure is a T4 with their fast path, not this laptop. On this GPU the decision is still a small slice of a spoken turn. The language model and speech synthesis are what the caller waits on.

Laya saves time only if it replaces a language-model router. The selected agent then gets a short body: the intent, the current sentence, and the history that intent needs. If two intents both clear the cutoff, those two agents run together. If none do, one general model answers.

Zero-shot confidence on a sample turn was soft (`book_meeting` 0.59, `take_note` 0.66, `needs_reply` choice `clarify` at 0.18). The base checkpoints are weak on unseen decision schemas. Fine-tune on real turns before trusting the probabilities.

## Subagents

Create each subagent once, as an object, and call only the ones Laya selects. Building them again on every turn costs more than the decision.

Each object holds:

- its own system prompt
- the slice of history it may see
- the call it makes

The meeting agent’s prompt is only scheduling. The note agent’s prompt is only how to write the note. The general agent is the fallback reply. Laya never sees those prompts.

Keep one Laya checkpoint on the GPU. The subagent objects should call a language-model API, so their prompts do not compete with Laya for the 3.6 GB.

## How speech-to-text streams text

The recognizer does not wait for the end of the sentence. While the person is still talking it sends snapshots.

- A **partial** is the current guess. The next message replaces it. “book a” becomes “book a meeting,” and earlier words in that guess can still change.
- A **final** locks a phrase. Later messages do not change it. The next partial starts empty and covers only the new audio. Locked phrases are appended: “book a meeting” plus “on Thursday.”
- The **pause** is the end of the turn. It does not send a new sentence. It means the utterance is finished. A short sentence may be one final and then the pause.

## Divide on final phrases

Partials are not sent into the graph. Each final phrase is appended, and Laya reads the whole locked sentence so far, not only the newest piece.

1. First final: “book a meeting.” Laya returns `book_meeting`. The meeting agent starts a draft. Nothing is spoken.
2. Next final: “on Thursday.” Laya runs again on “book a meeting on Thursday” while the previous draft is still in hand. Compare the intent and the slots the reply uses (day, person). The intent is the same, but the day is new, so the first draft is dropped and a new one is written from the full line. If the new phrase had not changed a slot, the first draft would be kept.
3. The pause speaks the draft that still matches the full line.

The same intent with a new day is a different reply. Speaking at the second phrase, before the pause, would play over anything the caller was about to add. A turn with only one final uses the pause as the check.

## First LangGraph iteration

Code is in `src/gnaniassignment/pipeline`. Run it with:

```bash
PYTHONPATH=src .venv/bin/python -m gnaniassignment.pipeline
```

`TurnSession` accepts `feed_final(phrase)` and `feed_end()`. The graph is one invoke per event: Laya decides, slots are read from the locked text (weekday words, and a name after “with”), and only the matching subagent objects run. Each object is created once and has its own system prompt. If the intent and the slots are unchanged, the previous draft is reused and the agent is not called again. `spoken` is set only on the pause.

Subagent reply text is still local, so the turn can run without a language-model API. Laya is the real checkpoint: one multilingual model, FP16, on the 1650 Ti.

Measured on “book a meeting” then “on Thursday”:

| Event | Intent | Slots | What happened |
|---|---|---|---|
| First final | `book_meeting` 0.91 | day none | Draft started. Nothing spoken. |
| Second final | `book_meeting` 0.89 | day thursday | Draft dropped and rewritten. |
| Pause | same | same | Draft reused. Spoken: “I can hold thursday. I will confirm before it is on the calendar.” |

The meeting agent ran twice, not a third time on the pause.
